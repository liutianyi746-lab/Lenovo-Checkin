# ADB 启动前恢复设计

## 目标

解决雷电模拟器关闭后遗留的 ADB 服务器或客户端卡死问题。每次签到任务启动雷电之前先恢复雷电自带 ADB，使 `adb devices` 不再因旧的 5037 服务阻塞；恢复范围仅限配置所指向的雷电 `adb.exe`，不得影响 Android Studio 或其他目录中的 ADB。

## 恢复流程

1. 解析现有配置并确定雷电 ADB 的绝对路径。
2. 在启动模拟器前执行有时限的 `adb kill-server`。
3. 若命令成功，继续执行有时限的 `adb start-server`。
4. 若 `kill-server` 超时或失败，在 Windows 上枚举进程，只选择 `ExecutablePath` 与雷电 ADB 绝对路径完全相同的进程并终止。
5. 确认目标路径的残留进程已清除后，再执行 `adb start-server`。
6. ADB 恢复成功后进入现有雷电启动、Android boot、App 导航和幂等签到流程。

## 组件边界

- `EmulatorManager` 新增 ADB 预检恢复方法，负责调用 ADB 命令并协调精确路径进程清理。
- Windows 进程清理由独立、可注入的函数完成；生产环境通过 PowerShell/CIM 查询 `ExecutablePath`，测试环境使用假执行器，不实际结束系统进程。
- `main.py` 不增加页面操作，也不改变签到判断；只在雷电启动前调用恢复方法。

## 安全边界

- 绝不使用 `taskkill /IM adb.exe`，因为它会结束所有同名进程。
- 只有进程的规范化绝对路径与 `find_adb_executable()` 返回值完全一致时才允许结束。
- 无法读取进程路径、路径为空、PowerShell 查询失败或目标不匹配时，不结束任何进程并返回明确错误。
- 所有外部命令都有超时，避免新的无限等待。

## 失败处理

- 常规 `kill-server` 成功时不触发强制清理。
- 常规命令卡死时记录警告和精确清理结果。
- 精确清理或 `start-server` 失败时停止本次任务，不启动雷电，并在日志中记录实际失败阶段。
- 无论后续签到成功或失败，仍使用现有流程关闭雷电；验证码和风控处理不变。

## 测试

- `kill-server` 成功时只执行常规重启，不调用强制清理。
- `kill-server` 超时时调用精确路径清理，然后成功启动 ADB。
- 强制清理只接收规范化后的目标 ADB 路径。
- 精确清理失败或 `start-server` 失败时抛出 `EmulatorError`，不会启动模拟器。
- 完整测试、Ruff、真实补跑和雷电关闭检查必须通过。
